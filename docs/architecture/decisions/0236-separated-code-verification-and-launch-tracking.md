# DR-0236: Separate code, verification and launch completion tracking

- Date: 2026-10-13 (Asia/Tokyo)
- Status: Accepted human request to reconstruct the confusing TODO; documentation-only implementation
- Scope: Live work ownership, evidence classification and original-criterion traceability

## Context

The previous live TODO combined four refactoring packages, eight Delivery 4
requirements and eight mainnet readiness groups. Twenty unchecked groups did
not mean twenty missing functions. It repeated shared acceptance requirements
and mixed parameterized code with real operators, key ceremonies, genesis
values, topology and public activation. Historical unexecuted captions also
appeared beside later actual scoped successes.

The human explicitly deferred real keys/backup operation, actual genesis and
public activation until network launch, while continuing ordinary code and
verification work. The new request is to reconstruct this tracker before more
product implementation, not to declare the product or a release complete.

Existing cache-hosted worktree registrations now point at absent paths. The
repository and committed c69/f093 source survive, but the cause of path absence
and recovery of uncommitted signing work/raw evidence are unknown. A registered
worktree or a remembered test is not proof of current file availability.

## Decision

Keep exactly the original twenty identities: R1-R4, Delivery 4's eight bullets
as D01-D08 in their original order, and M1-M8. Preserve the nine established
checked baseline entries. Do not manufacture completion by changing labels,
deferring a duty or reducing a test inventory.

Root TODO remains the only live status owner. Its two work sections distinguish
fourteen code/verification targets from six launch targets. Every row names
its target, known state and next step. The original full body is preserved in
development/history; only Markdown link destinations are rebased. The original
Git object remains the byte-exact source of that history.

Mixed M2/M4/M5 conditions retain their operational dependencies through
D04/D06/D07/M8. M6 records real economic/genesis approval, while its existing
parameterized author/inspector/install/supply code is identified separately.
A code-row check does not assert that all historical readiness conditions are
closed. Overall readiness requires the row's code/verification evidence plus
all mapped real-operation/launch obligations. No condition is waived merely
because it moves to the appropriate owner.

Selected-profile M3 host/power/storage/ENOSPC/resource-exhaustion,
real-writer-failover and TLS-failure/rotation qualification remains a
code/verification completion condition. D07 adds real-topology operational
rehearsal and cannot replace or defer that qualification.

The common acceptance record is referenced rather than copied into each row.
Evidence can serve several criteria only with the same actual source, selected
profile and scope. This is not permission to reuse an ancestor run, omit a
recipe or add new unrelated release prerequisites to an already scoped row.

Actual previously inspected success, currently available evidence, uncommitted
source, incomplete execution and release qualification are separate facts.
Preserve failed runs and missing evidence honestly. Recover available records
before deciding whether fresh verification is necessary; do not automatically
rerun consumed gates/helpers or pretend missing files remain available.

Use one cache-external checkout for this documentation change, rooted at the
retained c69 commit. Do not restore absent compiler targets or private inputs
by silently changing their identity. Product/environment restoration is a
separate bounded task, not a consequence of rewriting the tracker.

## Compatibility and original obligations

This changes no Rust, canonical bytes, schemas, dependency lock, actual test
selector, budgets, workflow lane or protocol authority. Preserve the full
required gate, applicable selected-source PG acceptance, thirteen-target A/B,
independent source/security/release review and actual supported-profile fault
criteria. Docker process death is not power/fsync/media or cross-file atomicity.

DR-0208 remains the explicit Native+SQLite-first and non-Ledger decision.
Other advertised providers retain their Phase 16/17 certification requirements;
local workerd or generic adapter tests do not complete them. Real roles/values
are not prerequisites to implementing parameterized code, but disposable
fixtures are not real operator independence or public readiness.

Protocol-v3 live activation still requires its original atomic-composition,
accepted-family authorization, protected signing and independent release gates.
This decision does not authorize deployment, public listeners, real keys,
host-wide resource/security changes, credential repair or provider-stopped task
retry. It creates no recurring automation and no new work window or goal.
