# DR-0282: Initial application operations with the recovered same-identity key

Date: 2026-10-30 (Asia/Singapore)

Status: Accepted source contract. Actual qualification belongs in TODO.md.

## Context

DR-0281 connects the later recovered application key to the six-stage Coin
consumer. Initial create-asset and initial own-created mint/burn run before
that path exists. Fresh application profiles have no earlier recovered key.
Moving the later `9a` or `9d` copy preparation would change their historical
original-reference-stop-before-copy and pre-existing-revocation chronology.

## Decision

Before the first create-asset, require the application profile's signer
registry to be empty, then use the existing custody-UID backup/restore helper
with its unused default `custody.seed.backup` and `custody.seed.restored`
paths under `/work/custody-keys`. Keep the existing nonempty stopped-signer
guard unchanged. Require absent destinations and private regular single-link
files, custody UID, mode 0600 and distinct paths/device-inodes. The two
existing-helper children finish their private copies and are waited before
any application signer starts.

Select that same early restored path for initial create-asset and initial
own-created mint/burn, including both revoked restarts. Record all four
selections from actual retained child argv and validate them in Python and
Node. Record preparation in a separate `initial_application_recovery`
object: three additive completion predicates, the exact two paths and
generated bytes, two private-copy children and zero extra CLI, PTY or signer
children. The existing 65-byte key format adds 130 logical bytes; retain the
helper's maximum of 512 bytes for the pair. Total private recovery copies
increase from six to eight per application profile. All historical
per-phase copy counts stay two.

Retain the original 47 application setup predicates, DR-0281's two added
predicates and every historical completion predicate. Preserve operation and
request order, pins, approvals, frames, signature comparisons, business
submissions, independent object/result/receipt/replay oracles, nonce, owner,
supply and exact counters. Initial create remains 3/3/2/1 then 1/1/0/1;
initial mint/burn remains 6/6/4/2 then 2/2/0/2. Preserve original isolation
probes and counters, all four whole profiles and every resource, capture,
PTY, transport and time limit.

Leave `9a`, `9d`, `a6`, `a7` and `a8` historical references, copies,
revocations and restarts in place. The six-stage consumer still selects its
later `own-recovered.seed.restored`. This is a consumer selection and early
fixture preparation within the existing trust contracts.

## Limits

Add no CLI operation, approval, signer, profile, identity, protocol encoding,
ownership policy or authority. No private bytes cross the existing custody
copy boundary. Historical requests remain signing-only. Source checks do
not establish actual distinct-UID execution, timing, capture or physical
resource headroom. Key rotation, creator/TreasuryCap migration, automatic
signing, real-key ceremony, complete M2 acceptance and public readiness are
separate conditions.
